# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal
Create a professional and responsive Requester-facing ticketing experience (MVP), allowing users to create tickets, view their tickets, and manage attachments, with a temporary Development Requester selection mechanism.

## 2. Stakeholder Request Interpretation
The IT department needs a system for Requesters (end-users) to submit support requests. The system must capture issue details (category, related system, priority, attachments) and assign a unique Ticket Number. Users should be able to view and search their own tickets. Since authentication is not yet ready, a temporary "Development Requester" selector will be used for testing.

## 3. Scope
### Included
- Temporary Development Requester Selection ("user login screen")
- Create Ticket workflow and validation
- My Tickets listing with search, filtering, sorting, and pagination
- Requester Ticket Detail view
- Attachment management (upload, soft-remove, download/preview restrictions)
- Database models and API for the above

### Excluded
- Real authentication and security (login, logout, passwords, roles)
- IT Staff workflow (dashboard, claiming tickets, changing IT Priority)
- Ticket collaboration (Public Comments, Internal Notes, Actions Taken)
- Ticket lifecycle beyond "New" status (resolving, closing)
- Administration functions (user/role management)

## 4. Functional Requirements
- **FR-01**: The system shall provide a screen to select an active Development Requester.
- **FR-02**: The system shall allow the selected Requester to create a new support ticket.
- **FR-03**: The system shall display a list of tickets owned by the selected Requester (My Tickets).
- **FR-04**: The system shall allow searching, filtering, sorting, and paginating the ticket list.
- **FR-05**: The system shall allow the Requester to view details of their own tickets.
- **FR-06**: The system shall allow attaching files (up to 5, max 5MB each, specific types) during ticket creation and in the Ticket Detail view.
- **FR-07**: The system shall allow soft-removal of attachments by the owner.

## 5. Business Rules
- **BR-01**: The official Ticket Number is generated by the backend and must be unique.
- **BR-02**: A new Ticket begins with Current Status `New`.
- **BR-03**: Lab 2 uses a Development Requester selector instead of login. The selected identity is for testing only and is not authentication.
- **BR-04**: Attachments must be of type JPG/JPEG, PNG, WEBP, or PDF.
- **BR-05**: Maximum attachment size is 5 MB per file.
- **BR-06**: Maximum active attachments per Ticket is 5.
- **BR-07**: Attachment removal is a soft-removal. Removed files must not be downloadable or previewed.
- **BR-08**: A Requester can only view and manage their own tickets (Ownership protection).
- **BR-09**: Ticket Summary and Description are required fields. Validation fails if empty or only whitespace.
- **BR-10**: Inactive Requesters must not be loaded into the Development Requester selection screen.
- **BR-11**: The system must display a clear "Empty State" message and graphic if a Requester has no tickets.
- **BR-12**: The system must display a "No Results" message if search or filter yields zero tickets.
- **BR-13**: In case of a submission failure or API error, the user's filled data in the form must be preserved to prevent data loss.

## 6. UI Specification Summary
- Implement "Zen Green Theme" (Primary: #006B3C, Secondary: #0B7A46, Pale green: #EAF6EF).
- Reusable form, list, badge, validation, loading, empty, and error conventions.
- Responsive layout across Desktop (>= 992px), Tablet (768-991px), and Mobile (< 768px).
- Accessibility: Focus indicators, keyboard navigation, and proper labels for screen readers.
- For detailed UI rules, refer to `ui-spec.md`.

## 7. Data Changes
- **Models to add/update**: 
  - `RequesterUser`: id, name, email, isActive
  - `Category`: id, name
  - `RelatedSystem`: id, name
  - `Ticket`: id, ticketNumber, summary, description, status, priority, requesterId, categoryId, relatedSystemId, createdAt
  - `Attachment`: id, ticketId, originalFileName, storedFileName, size, mimeType, isRemoved
- **Relationships**: Requester 1:N Ticket, Ticket 1:N Attachment, Category 1:N Ticket, RelatedSystem 1:N Ticket.
- **Seed Data**: 4 categories, 6 related systems, 4 active requesters, 1 inactive requester. Safe to run repeatedly.

## 8. API Contract
- **GET /api/requesters**: Retrieve active Development Requesters
- **GET /api/categories**: Retrieve Categories
- **GET /api/related-systems**: Retrieve Related Systems
- **POST /api/tickets**: Create a Ticket (includes attachment metadata)
- **GET /api/tickets**: Retrieve paginated list of owned tickets (params: page, search, category, etc.)
- **GET /api/tickets/:id**: Retrieve details of one owned ticket
- **POST /api/tickets/:id/attachments**: Upload an Attachment
- **DELETE /api/tickets/:id/attachments/:attachmentId**: Soft-remove an Attachment

## 9. Acceptance Criteria
- **AC-01 (Create)**: Given valid Ticket data, when the Requester submits the form, then one Ticket is saved and the official Ticket Number is displayed.
- **AC-02 (Context)**: Given no Development Requester is selected, when the user attempts to open My Tickets, then the Requester Selection screen is shown.
- **AC-03 (Ownership)**: Given Requester B is selected, when a Ticket belonging to Requester A is requested, then the Ticket data is not returned (403 Forbidden or 404 Not Found).
- **AC-04 (Validation)**: Given missing required fields (e.g. Summary), when the user submits, then validation error messages appear next to the fields and API is not called.
- **AC-05 (Attachment - Size)**: Given a file larger than 5MB, when the user tries to upload, then validation fails and an error message is shown.
- **AC-06 (Attachment - Remove)**: Given an uploaded attachment, when the user soft-removes it, then it is marked as removed and can no longer be downloaded.
- **AC-07 (Pagination)**: Given a Requester has 15 tickets and page size is 10, when they view My Tickets, then they see 10 tickets on page 1, and can navigate to page 2 to see the remaining 5.
- **AC-08 (Search/Filter)**: Given the user applies a search term "wifi", when the list updates, then only tickets containing "wifi" in their summary or description are shown.
- **AC-09 (Empty State)**: Given a newly selected active Requester with 0 tickets, when they view My Tickets, then an empty state graphic and "Create Ticket" call-to-action are displayed.
- **AC-10 (Error Preservation)**: Given the backend server is down, when the user submits a filled Create Ticket form, then an error message is shown, but the form data is not erased.
- **AC-11 (Responsive)**: Given the viewport is < 768px (Mobile), when the user views the Create Ticket form, then fields stack vertically without horizontal scrolling.

## 10. Definition of Done
- Implementation of all approved scope and business rules.
- Satisfaction of all acceptance criteria.
- Automated tests (Unit, API, UI, E2E) pass and are traceable to ACs.
- Conformance to Zen Green UI and responsive specifications.
- Peer review approved in GitHub.
- README and required documentation updated.
- Final PDF submission created with required screenshots.

## 11. Assumptions and Decisions
- Ticket Number format: `TKT-YYYY-XXXXXX` (generated securely on backend).
- We will store the selected `requesterId` in frontend state/localStorage for testing context.
- Attachment files will be saved to local disk for this MVP rather than cloud storage.
